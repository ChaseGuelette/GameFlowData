## Work Completed

### 1. Problem Diagnosis

**Discovery:** The `--scrape-injuries` flag in `run_daily.py` was calling `injury_scraper_job.py`, which writes to `espn_injuries` table using ESPN as the data source. However, all downstream ML components use `rapidapi_injuries`:

| Component | Table Used | Source |
|-----------|------------|--------|
| Feature Store (`feature_store.py`) | `rapidapi_injuries` | RapidAPI |
| Daily Runner (`daily_runner.py`) | `rapidapi_injuries` | RapidAPI |
| Backtest Harness | `rapidapi_injuries` | RapidAPI |
| `--scrape-injuries` flag (OLD) | `espn_injuries` | ESPN |

**Impact:** Daily injury data was effectively unused — the scraper wrote to one table, but predictions used a different (stale) table.

### 2. Solution Design

Evaluated three options:
- **Option A (chosen):** Adapt `rapidapi_injury_backfill.py` to run for today's date
- **Option B:** Switch feature store/daily runner to use `espn_injuries` (loses `player_id` matching)
- **Option C:** Build a bridge to sync ESPN data into `rapidapi_injuries` format (complex)

Option A was chosen because:
- Minimal code changes (reuses existing, tested modules)
- Maintains data source consistency (RapidAPI everywhere)
- Preserves `player_id` linking for feature generation
- `rapidapi_injury_backfill.py` already supports single-day scraping via `--start` and `--end` flags

### 3. Implementation

## Design Decisions

1. **Reuse over rewrite:** Rather than creating a new "daily injury scraper" module, we reused `rapidapi_injury_backfill.py` which already supports single-day fetching via `--start` and `--end` flags. This minimizes risk and maintains code consistency.

2. **Always run linker:** The linker runs every time even if no new records were scraped. This is safe because it only processes rows where `player_id IS NULL`, so it's idempotent. This ensures any previously unlinked records get processed.

3. **Keep ESPN scraper:** The ESPN injury scraper (`injury_scraper_job.py`) and `espn_injuries` table are not removed. They may still be useful for comparison or backup purposes.

## Environment Requirements

For the injury scraper to work:

## E5: Paper Trading Infrastructure

### 7. Design Decisions

Based on user input:
- **Standalone scripts** — not integrated into `run_daily.py`; designed for future lightweight dashboard
- **Stats supported** — pts, reb, ast only (matching current model coverage)
- **SQL storage** — bets stored in tables for dashboard display

### 8. Database Tables

Created via Supabase migration:

**`paper_bets`** — Individual bet records
- `prediction_id`, `game_date`, `player_id`, `player_name`, `stat_type`, `line`, `bet_direction`
- `odds_at_bet`, `implied_prob`, `model_prob`, `edge`, `stake`, `kelly_fraction`
- `status` (pending/won/lost/push/cancelled), `actual_value`, `pnl`, `placed_at`, `resolved_at`
- Unique on `(game_date, player_id, stat_type, bet_direction)`

**`paper_trading_daily_log`** — Daily aggregates
- `game_date`, `total_bets`, `bets_won`, `bets_lost`, `bets_push`, `bets_pending`
- `total_staked`, `total_pnl`, `roi_pct`, `cumulative_pnl`, `bankroll_after`
- Unique on `game_date`

### 9. Implementation

**`src/paper_trading/paper_trader.py`** — Core `PaperTrader` class:
- `select_bets(game_date)` — Query daily_predictions, filter by edge threshold, calculate Kelly stakes
- `place_bets(bets)` — UPSERT into paper_bets table
- `resolve_bets(game_date)` — Fetch actuals from player_game_stats, update status/P&L
- `_update_daily_log()` — Aggregate stats and update daily log
- Dashboard query methods: `get_pending_bets()`, `get_daily_summary()`, `get_bets_for_date()`

**`src/paper_trading/place_bets.py`** — CLI for placing bets:


**`src/paper_trading/resolve_bets.py`** — CLI for resolving bets:
```bash

```

### 10. Bet Selection Logic

From `daily_predictions` for each prediction:
1. Check if `over_edge` or `under_edge` exceeds threshold (default 5%)
2. Select direction with higher edge
3. Filter extreme odds (-200 to +200 range)
4. Calculate stake via fractional Kelly (default 12.5%)
5. Cap at max 5% of bankroll per bet

### 11. Resolution Logic

1. Fetch pending bets for game_date
2. Query `player_game_stats` for actual stat values
3. Compare actual vs line → determine outcome:
   - `actual > line` and direction=over → won
   - `actual < line` and direction=under → won
   - `actual == line` → push
   - Player didn't play → cancelled
4. Calculate P&L: won = stake × (decimal_odds - 1), lost = -stake
5. Update `paper_bets` and `paper_trading_daily_log`
