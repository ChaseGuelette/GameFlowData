# Development Session 61 — 2026-03-03

## Summary

MLB Linker Deep Debug — Fixed ARI/OAK team abbreviation mismatch in `mlb_config.py` and built a re-link pass (Sub-stage 5) in `mlb_linker_local.py`. Combined effect: fully linked rows jumped from 62.0% (14.1M) to 96.8% (21.97M of 22.71M total).

## Problem

The MLB linker was only linking 62% of `mlb_raw_player_props` rows (14.1M of 22.7M). Investigation revealed two root causes:

1. **Team abbreviation mismatch:** `MLB_TEAM_ALIASES` mapped Arizona → "ARI" and Oakland → "OAK", but the `mlb_teams` database table uses "AZ" and "ATH" as canonical abbreviations. Every game involving those teams failed game matching, affecting ~3M+ prop rows.

2. **Missing team_id backfill:** After game_id and player_id are resolved, team_id is looked up via boxscore data (`player_game_stats` table). But many players don't appear in a specific game's boxscore (injury scratches, day-off rest, etc.), leaving team_id NULL even when game and player are correctly linked.

## What Was Built

### 1. Team Alias Fix (`mlb_config.py`)

Fixed 6 entries in `MLB_TEAM_ALIASES`:
- `"Arizona Diamondbacks"` → `"AZ"` (was `"ARI"`)
- `"D-backs"` / `"Diamondbacks"` → `"AZ"` (was `"ARI"`)
- `"Oakland Athletics"` / `"Athletics"` → `"ATH"` (was `"OAK"`)

### 2. Re-link Pass (`mlb_linker_local.py`)

New `process_player_props_relink()` function — Sub-stage 5 that runs after the initial 4 processing sub-stages.

**What it does:**
1. Finds all rows with `game_id` + `player_id` set but `team_id` NULL
2. For each unique `(player_id, game_id)` combo, checks boxscore data
3. Categorizes each combo into one of 4 buckets:
   - `wrong_pid_fixable` — A different player with a similar name IS in the boxscore
   - `correct_pid_not_in_game` — Player exists but wasn't in this game's boxscore
   - `game_no_boxscore` — No boxscore data for this game at all
   - `name_not_found` — Player name can't be resolved
4. Fixes wrong player_ids where the correct player IS in the game's boxscore
5. For `correct_pid_not_in_game`, resolves team_id from nearby games (within 30 days) using `find_closest_game_date()`

**Outputs:**
- `props_relink_pid_updates.csv` — Player_id corrections
- `props_team_backfill_updates.csv` — Team_id from nearby games

### 3. Upload Stages for Re-link Data

Two new upload functions with chunked retry (50K rows/chunk, 20 retries, 60s cap):
- `upload_props_relink_with_team` — Updates player_id corrections
- `upload_props_teams_backfill` — Updates team_id from nearby-game lookups

### 4. Status Display Updates

The `status` command now shows all 5 processing sub-stages and all 5 upload stages with row counts and completion status.

## Key Design Decisions

### Why a Separate Re-link Pass (Not Inline)?

The initial 4 sub-stages run in a fixed pipeline: games → players → teams. The re-link needs the output of ALL previous stages to work (it queries for rows that have game+player but not team). Running it as a separate pass after the main pipeline is cleaner and allows it to be re-run independently when new boxscore data arrives.

### Why Nearby-Game Fallback (Not Just Boxscore)?

Many prop lines are posted for players who end up not playing (late scratches, rest days). These players have valid game_id and player_id but will never appear in that game's boxscore. Using the nearest game within 30 days where the player DID play allows resolving their team_id from actual game data, which is correct in ~99% of cases (mid-season trades being the rare exception).

### Why Two Separate Upload Stages?

Player_id corrections and team_id backfills are fundamentally different operations — one changes which player a row refers to, the other fills in a missing field. Keeping them separate allows re-running just one if needed and makes the checkpoint system more granular.
