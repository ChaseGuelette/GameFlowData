# Development Session 58 — 2026-03-02

## Summary

Pipeline Resilience Overhaul — made the scheduler self-healing, dependency-aware, and transparent about failures. The 9 AM daily stats job was the system's single point of failure: when it timed out, the entire downstream pipeline silently degraded with no user-visible signal. This session adds job status tracking, per-step retries, dependency gates, automatic retries, and stale-data transparency.

## Problem

The 9 AM daily stats job timing out caused a silent cascade:
- Inference ran with stale rolling averages (no warning)
- Edge refresh recalculated against stale MC samples (no warning)
- Dashboard showed "fresh" predictions built on yesterday's data
- The existing staleness check in `inference_job.py` used a >2 day threshold that wouldn't even trigger on same-day failures
- ISS-039 ("scheduler has no job dependency enforcement") was marked Fixed but only added a warning log that doesn't block execution

## What Was Built

### 1. Job Status Tracking (scheduler.py)

- **In-memory `JOB_STATUS` dict** — Updated by `run_job()` after every execution with status, end_time, and duration
- **`record_job_execution()` helper** — Writes to `job_executions` Supabase table for persistent history (non-fatal)
- **`job_executions` table** — New migration `007_job_executions.sql` with index on `(job_name, started_at DESC)`

### 2. Per-Step Retries with Backoff (daily_stats_job.py)

Extended `run_command()` with `max_retries`, `retry_delay`, and `timeout` parameters:

| Step | Timeout | Retries | Notes |
|------|---------|---------|-------|
| 1. NBA Scrape | 10m | 2 | Critical |
| 2. Linker | 10m | 2 | Critical |
| 3. Team IDs | 5m | 0 | Non-critical |
| 4. Positions | 5m | 0 | Non-critical |
| 5. League Avgs | 5m | 0 | Non-critical |
| 6. Rolling Avgs | **20m** | **2** | Most common timeout culprit |
| 7. Opponent Stats | **15m** | **2** | Critical |

Retries use exponential backoff: 15s → 30s → 60s between attempts. Global scheduler timeout increased from 30m → 45m.

### 3. Dependency Gate (scheduler.py)

- `check_dependency(upstream_job, max_age_hours)` — Queries `JOB_STATUS` to verify upstream succeeded recently
- `run_inference()` checks `daily_stats_job.py` succeeded in last 8 hours
- If stale: passes `--stale-warning` flag, sends Discord alert, but still runs inference (stale data > no data)

### 4. Stale Data Warning (inference_job.py)

- Added `--stale-warning` CLI flag (set by scheduler dependency check)
- Changed staleness check from `days_stale > 2` to `latest_game_date < yesterday`
- Sets `data_stale` flag and propagates to Discord alerts
- Sends separate "Stale Data Warning" Discord alert
- Inference never hard-fails — L5 averages have 4/5 overlap, L15 has 14/15 overlap

### 5. Edge Refresh Improvements (edge_refresh_job.py)

- Changed "No MC samples" exit from warning to info-level "NO-OP" message (expected before first inference)
- Added MC sample staleness check: if samples >6 hours old, logs warning and sends Discord alert

### 6. Automatic 9:30 AM Retry (scheduler.py)

- `run_daily_stats_retry()` at 14:30 UTC checks if 9 AM run succeeded
- If not, re-runs daily stats (gives the system a second chance before inference at 12:15 PM)
- If already succeeded, skips silently

## Key Design Decisions

### Why Not Hard-Fail on Stale Data?

Running inference with slightly stale rolling averages is **better** than producing zero predictions:
- L5 averages have 4/5 game overlap (80% of data is still current)
- L15 averages have 14/15 overlap (93% current)
- Zero predictions blacks out the dashboard, paper trading, and edge refresh for the entire day
- The stale-data Discord alert makes the degradation visible

### Why In-Memory + DB for Status Tracking?

- **In-memory (`JOB_STATUS`)**: Fast lookups for dependency checks within the same scheduler process
- **DB (`job_executions`)**: Persistent history survives restarts, queryable from dashboard or debugging sessions

### Why 20m Timeout for Step 6?

Step 6 (`populate_average_stats_incremental.py`) was the most common timeout culprit in production. The 10-minute timeout was too tight when multiple players had games — doubling to 20m addresses the immediate production issue while retries handle transient DB/network failures.
