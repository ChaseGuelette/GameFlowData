# Development Session 60 — 2026-03-03

## Summary

Faster Lines Pipeline — persistent fuzzy cache for NBA linker, parallel step execution in lines_job, and 5-minute props refresh cadence. Combined effect: full mode ~90s → ~45-55s, props-only linker step ~15s → <1s, 2x fresher odds data.

## Problem

The lines job runs every 10 minutes and takes 90-100 seconds. Breakdown:
- Props scraper: ~23s (API calls, can't shrink)
- NBA linker: ~15s (redundant O(n*m) fuzzy matching — same ~50 names every run)
- Injury scraper + linker: ~12s (runs serially with props, but is independent)
- Overhead (imports, DB connections): ~20-35s

The 90s runtime at 10-minute intervals means lines are up to 12 minutes stale during games. Goal: cut runtime to enable 5-minute frequency for fresher odds.

## What Was Built

### 1. Persistent Fuzzy Cache (`nba_linker_local.py`)

**New functions:**
- `_load_fuzzy_cache()` — Reads `linker_data/_fuzzy_cache.json`, returns `(cache_dict, player_count)` for invalidation
- `_save_fuzzy_cache()` — Writes cache to disk after processing
- `_resolve_fuzzy_names()` — Batch SequenceMatcher on unique unmatched names (0.80 threshold, +0.15 last name bonus). Ported from MLB linker pattern.

**Refactored player matching in both `link_incremental()` and `process_local()`:**

Old: Per-row `match_player()` that loops through all ~600 players with SequenceMatcher for every single row.

New: 3-step batch pipeline:
1. Manual mappings via `.map(manual_mappings)` — vectorized
2. Exact normalized match via `.map(player_lookup)` — vectorized
3. Fuzzy cache lookup for remaining unmatched — only truly new names trigger `_resolve_fuzzy_names()`

**Cache invalidation:** Stores `player_count` alongside cache. If player count changes (new player added), entire cache is cleared and rebuilt.

**Expected impact:** ~15s → <1s on typical runs (95%+ cache hits).

### 2. Parallel Step Execution (`lines_job.py`)

**New `--parallel` flag** splits steps into two independent groups:
- Group A (props path): game_lines_scraper → props_scraper → nba_linker
- Group B (injury path): injury_scraper → injury_linker

When `--parallel` is set, both groups run concurrently via `threading.Thread`. Each group runs its steps serially internally.

**New helpers:**
- `run_step_group(steps, dry_run)` — runs steps serially, returns success bool
- `run_parallel_groups(groups, dry_run)` — runs groups concurrently, collects results

**Backward compatible:** Without `--parallel`, identical sequential behavior.

**Expected impact:** Full mode ~90s → ~45-55s (wall clock = max of two paths).

### 3. Scheduler Updates (`scheduler.py`)

- Props-only cron: `*/10` → `*/5` (every 5 minutes)
- Edge refresh cron: `2,12,22,32,42,52` → `2,7,12,17,22,27,32,37,42,47,52,57`
- New `run_lines_full_parallel()` wrapper
- Noon/4pm full runs updated to use `--parallel`
- ~156 runs/day each (up from ~78)

**API credit impact:** ~6,400/day × 31 = ~200K/month — 4% of 5M monthly quota.

## Key Design Decisions

### Why File-Based Cache (Not In-Memory)?

The MLB linker uses in-memory-only cache (resets each run). The NBA linker runs every 5 minutes seeing the same ~50 player names — persisting to disk means fuzzy matching only happens once per unique name *across all runs*, not just within a single run. The ~15s savings per run compound to significant time at 156 runs/day.

### Why Threads (Not Subprocesses) for Parallel Groups?

The groups are themselves running subprocesses internally (via `subprocess.run`). Using `threading.Thread` avoids subprocess-within-subprocess complexity and is simpler than `multiprocessing`. Since the threads are I/O-bound (waiting on subprocesses), the GIL isn't a bottleneck.

### Why Not Parallel the Props-Only Mode?

Props-only mode has no injury steps to parallelize — it's just 2 serial steps (scrape → link). The `--parallel` flag is only useful for full mode.
