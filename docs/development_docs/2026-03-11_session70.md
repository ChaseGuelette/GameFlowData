# Development Session 70 -- 2026-03-11

## Summary

Fixed scheduler timezone double-conversion bug causing 4 jobs to fire at wrong times, and tuned calibration drift alerts to stop false-flagging the model's intentional under-prediction as drift.

## What Was Fixed

### Scheduler Timezone Bug (`src/orchestration/scheduler.py`)

The scheduler uses `BlockingScheduler(timezone="America/New_York")`, which means APScheduler interprets all CronTrigger hour values as ET. However, several triggers were written using UTC-converted hours (the developer intended them as UTC), causing double-conversion — APScheduler treated the already-converted UTC hours as ET.

**Impact:**

| Job | Before (actual ET fire time) | After (correct ET) |
|-----|-----|-----|
| `daily_stats_retry` | 2:30 PM | 9:30 AM |
| 5-min props refresh | 4 PM – 4:57 AM | 11 AM – 11:57 PM |
| 5-min edge refresh | 4 PM – 4:57 AM | 11 AM – 11:57 PM |
| 4 PM full lines scrape | 9 PM | 4 PM |

**Changes:**
- `CronTrigger(hour=14, minute=30)` → `CronTrigger(hour=9, minute=30)` (retry)
- `CronTrigger(hour='16-23,0-4', ...)` → `CronTrigger(hour='11-23', ...)` (5-min jobs)
- `CronTrigger(hour=21, minute=0)` → `CronTrigger(hour=16, minute=0)` (4 PM lines)
- Removed all misleading `(HH:MM UTC)` annotations from docstring
- Removed stale `# UTC: hour 16-23 and 0-4 (EST = UTC-5)` comment

**Jobs already correct (no changes):** `daily_stats` (hour=9), `lines_noon_full` (hour=12), `inference_noon` (hour=12, minute=15), `inference_4pm` (hour=16, minute=15).

### Calibration Drift False Alarms (`src/paper_trading/calibration_monitor.py`)

The calibration monitor's `CalibrationMetrics.all_alerts` property included `bias_alerts`, which flagged the model's systematic under-prediction relative to actual values. This is expected behavior — the model predicts lower than the market, which is the source of edge (confirmed in Session 67 research). The bias alerts were inflating severity to "warning"/"critical" on Discord.

**Fix:** Excluded `bias_alerts` from `all_alerts` (which drives severity). Bias data still renders in the Discord embed for visibility — if the bias suddenly flips or changes magnitude, it's still observable. It just no longer triggers false alarms.

**Design rationale:**
- Removing bias entirely would lose visibility into changes
- Keeping it informational is the right balance
- Severity is now driven only by: quantile coverage, probability calibration (ECE/Brier), and edge accuracy
