# Development Session 38 — 2026-02-18

## Summary

Fixed Railway deployment pipeline — three root causes preventing jobs from running successfully on Railway, all resolved. Lines job now completes all 5 steps and sends Discord success alert.

## Context

After pushing commits (social media image generator, GitHub Actions pytest CI), Railway wasn't redeploying automatically, and when manually redeployed, jobs failed with multiple errors: Nix immutable filesystem blocking pip, missing Python packages in subprocesses, and missing shared libraries for C extensions.

## Problems Found & Fixed

### Problem 1: Nix Immutable Filesystem (`externally-managed-environment`)

**Symptom:** Build failed with `externally-managed-environment` error — `ensurepip` tried to write to read-only `/nix/store`.

**Root cause:** Previous `nixpacks.toml` used `python3.11 -m ensurepip --upgrade` which attempts to modify the Nix-managed Python installation.

**Fix:** Replaced with a Python venv approach:
```toml
[phases.install]
cmds = [
    "python3.11 -m venv --system-site-packages /app/venv",
    "/app/venv/bin/python -m pip install -r requirements.txt"
]
```
The `--system-site-packages` flag lets the venv inherit pip from `python311Packages.pip` without modifying the Nix store.

### Problem 2: Hardcoded `python` in Subprocess Calls

**Symptom:** Jobs failed with `ModuleNotFoundError: No module named 'requests'` (and pandas, dotenv) even though packages were installed in the venv.

**Root cause:** `lines_job.py`, `daily_stats_job.py`, and `run_daily.py` all used hardcoded `"python src/scrapers/..."` when spawning subprocesses. On Railway, bare `python` resolves to the system Nix Python (`/nix/store/.../bin/python3.11`) which has no pip-installed packages. The scheduler itself used `sys.executable` correctly, but the job scripts it called did not.

**Fix:** Replaced all `"python ..."` with `f"{sys.executable} ..."` across all three orchestration files. Since the scheduler starts with `/app/venv/bin/python`, `sys.executable` propagates the venv Python to all subprocess layers.

### Problem 3: Missing Shared Libraries at Runtime

**Symptom:** First 4 job steps passed (they don't use numpy), but step 5 (`nba_linker_local.py`) failed with `ImportError: libz.so.1: cannot open shared object file`.

**Root cause:** numpy's C extension (`_multiarray_umath`) dynamically links to `libz.so.1`. Even though `zlib` was added to nixPkgs, `nix-collect-garbage -d` could remove it if not properly referenced, and more importantly, `LD_LIBRARY_PATH` wasn't set so the dynamic linker couldn't find libraries in `/root/.nix-profile/lib/`.

**Fix:** Two changes to `nixpacks.toml`:
1. Added `zlib` and `stdenv.cc.cc.lib` to nixPkgs (provides libz.so.1 and libstdc++.so.6)
2. Added `[variables] LD_LIBRARY_PATH = "/root/.nix-profile/lib"` so the dynamic linker can find them

### Bonus: Empty watchPatterns

**Finding:** Railway dashboard showed `watchPatterns: []` and `ignoreWatchPatterns: true` on the service, which is why git pushes weren't triggering auto-deploys. This needs to be cleared in the Railway dashboard (not a code fix).

## Key Lessons

1. **Nix + Python venv is the correct pattern** — Never try to install packages into the Nix store directly. Use a venv with `--system-site-packages`.
2. **Always use `sys.executable` for subprocesses** — Hardcoded `python` is fragile and resolves differently across environments (local, Docker, Nix).
3. **`LD_LIBRARY_PATH` is essential for Nix-based containers** — Nix installs libraries to `/nix/store/...` which isn't on the default library search path. Without `LD_LIBRARY_PATH`, C extensions can't find shared libraries at runtime.
4. **Debug iteratively on Railway** — Used 2-minute one-shot test jobs to iterate quickly instead of waiting for scheduled cron times.
