Central feature engineering with 28 features across 6 data sources:

**Feature Groups:**
- Pitcher rolling averages (10): SO L3/L5/SZN, K/9 L5, IP L3/L5/SZN, pitches L3, BB L5, std SO L3

**SQL Pattern:** LATERAL JOIN mirroring NBA `feature_store.py._load_single_season_training()`. Joins pitching game stats, rolling averages, Statcast averages, FanGraphs season stats, park factors, game lines, and prop lines.

**Methods:** `get_training_dataset()`, `get_player_game_features()`, `get_features_for_date()`, `enrich_with_matchup_features()`

### 5. `src/models/mlb/mlb_quantile_trainer.py`
`MLBPitcherKPipeline` wrapping the existing `QuantileModelSuite`:
- Trains directly on SO counts (no minutes decomposition needed for MLB)
- Default config: 1000 estimators, depth 5, lr 0.03, Q10-Q90
- Save/load via joblib to `pitcher_k_model.joblib` + `pitcher_k_feature_config.joblib`
- Supports per-quantile feature selection (same as NBA)

### 6. `src/models/mlb/mlb_monte_carlo.py`
`MLBMonteCarloPredictor` for inverse CDF sampling:
- No copula (single stat, no minutes-rate correlation to model)
- No blowout factor (not applicable to pitching)
- Integer rounding after sampling (strikeouts are whole numbers)
- `ZERO_SNAP_THRESHOLD = 0.3` (snaps near-zero values to 0 in extended quantile function)
- Batch prediction via batched XGBoost calls + per-player numpy sampling
- Reuses `PropPrediction` dataclass from NBA code (sport-agnostic)

## Key Design Decisions

### Why No Minutes Decomposition?
NBA models predict minutes × stat-per-minute because minutes are the primary source of variance (injuries, blowouts, foul trouble). In MLB, the starting pitcher's workload is less variable — starters typically pitch 5-7 innings. Predicting SO directly captures more signal than factoring through IP × K-rate.

### Why No Copula?
Copula is needed when jointly sampling correlated variables (NBA uses it for minutes and rate). Pitcher K is a single output — there's no second variable to correlate with. If we later add a pitcher outs model and want K|IP correlation, copula can be added then.

### Why Higher Edge Thresholds?
MLB prop markets have wider juice (higher vig) than NBA. At 5% edge threshold, too many bets would be placed on lines with no real value. 8% for pitcher K and 10% for batter stats filters more aggressively.

### Why Reuse vs Rewrite?
`QuantileModelSuite` is already generic — it takes feature lists as constructor params and trains XGBoost per-quantile. `PropPrediction` is sport-agnostic. No need to duplicate 500+ lines of tested code. Only `PlayerPropsModelPipeline` is NBA-specific (minutes + rate structure), so we bypass it with `MLBPitcherKPipeline`.
