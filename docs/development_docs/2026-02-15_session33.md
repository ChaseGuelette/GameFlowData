### 1. Railway Deployment Fix

**Problem:** Railway build failing with "No module named pip" error.

**Root Cause:** Railway's Nixpacks builder wasn't properly installing pip before attempting to run `pip install`.

**Solution:** Created `nixpacks.toml` with explicit pip installation:

```toml
[phases.setup]
nixPkgs = ["python311", "python311Packages.pip"]

[phases.install]
cmds = [
    "python3.11 -m ensurepip --upgrade",
    "python3.11 -m pip install --upgrade pip",
    "python3.11 -m pip install -r requirements.txt"
]

[start]
cmd = "python3.11 src/orchestration/scheduler.py"
```

### 4. Feb 11 Model Picks Bug Fix

**Problem:** Feb 11, 2026 showed only 2 Model Picks when there should be 13.

**Root Cause:** Supabase returns bigint values inconsistently as either number or string. When using `Map.get()`, a number key like `123456` won't match a string key `"123456"`.

**Solution:** Use `String()` conversion on Map keys for consistent lookup:

```tsx
// Create maps with string keys
const recommendedMap = new Map<string, boolean>()
for (const p of predictionsData) {
  const key = String(p.id)  // Always convert to string
  recommendedMap.set(key, p.is_recommended ?? false)
}

// Look up with string key
const enrichedBets = betsData.map(bet => {
  const key = String(bet.prediction_id)  // Match the key format
  return {
    ...bet,
    is_recommended: recommendedMap.get(key) ?? false,
  }
})
```

### Supabase BigInt Handling

JavaScript's Number type can represent integers up to 2^53-1 safely. Supabase returns larger integers (like database IDs) as bigint, which JavaScript may represent as either a number or a string depending on the exact value and client configuration.

The safest approach when using database IDs as Map keys is to always convert to string using `String(id)` for both storage and lookup.
