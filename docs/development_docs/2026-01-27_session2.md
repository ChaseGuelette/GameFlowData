## Diagnosis

### Root Cause: Pandas 3.0 + XGBoost 3.1.3 Incompatibility

**Versions:** XGBoost 3.1.3, Pandas 3.0.0, NumPy 2.4.1

Pandas 3.0 changed the `Index` dtype from `object` to `str`. XGBoost's `DMatrix` constructor relies on the old `object` dtype to detect feature names from DataFrames. With pandas 3.0:

```python
df = pd.DataFrame({'a': [1.0], 'b': [2.0]})
dmat = xgb.DMatrix(df)
print(dmat.feature_names)  # None — should be ['a', 'b']
```

When the DMatrix has `feature_names: None` but the model's booster has stored feature names (from training), XGBoost raises:
> "data did not contain feature names, but the following fields are expected: ..."

**Key finding:** The model was trained with XGBoost 3.1.3 (confirmed via `booster.save_config()` version field `[3, 1, 3]`). The model's `feature_names_in_` contains `np.str_` objects. The training likely happened before the pandas 3.0 upgrade, or the feature name extraction worked during training because the model hadn't stored feature names yet at that point.

**Why it wasn't caught earlier:** The `_prepare_features` function in `monte_carlo.py` correctly builds a pandas DataFrame with proper column names and float32 dtypes. The DataFrame looks perfect — the bug is invisible at the Python level. XGBoost's internal C++ layer just can't read the feature names from the new pandas Index type.

## What I Shipped

### 1. XGBoost Pandas 3.0 Compatibility Fix (`src/models/quantile_trainer.py`)

Single-line fix in `predict_quantiles()` (line 257):

**Before:**
```python
predictions[f"q{int(q * 100):02d}"] = model.predict(X_q)
```

**After:**
```python
predictions[f"q{int(q * 100):02d}"] = model.predict(
    X_q, validate_features=False
)
```

**Why this is safe:** `_prepare_features()` constructs the DataFrame using the model's own `all_feature_names` list, then `predict_quantiles` slices with `X[q_features]` where `q_features` comes from `feature_names_per_quantile`. Feature order is guaranteed correct by construction — the validation check is redundant.

**Scope:** Only the inference-time `predict_quantiles()` call needed fixing. Training-time `.predict()` calls (in `train()` and `get_learning_curve_data()`) don't hit this because freshly-created models don't have stored feature names to validate against.

## Decisions Made

1. **`validate_features=False` over package downgrade**: Downgrading pandas to 2.x would fix the issue but could break other code relying on pandas 3.0 features. The `validate_features=False` workaround is surgical and safe given our controlled feature pipeline.

2. **No changes to `_prepare_features`**: Considered converting to `DMatrix(array, feature_names=...)` explicitly, but this would require changing the return type from DataFrame to DMatrix, cascading changes through the API. The one-line fix is simpler.

3. **Left other `.predict()` calls unchanged**: Training-time calls in `train()`, `get_learning_curve_data()`, `feature_selection.py`, and `hyperparameter_tuner.py` don't need the fix because models don't have stored feature names during training.
