### 2. API Route — `/api/ask`

**File:** `dashboard/src/app/api/ask/route.ts` (new)

- **Auth:** Server-side Supabase client (same pattern as `/api/slate/route.tsx`). Returns 401 if not authenticated.
- **Rate limiting:** In-memory `Map<userId, timestamps[]>` with 20 questions per 24-hour rolling window. Returns `remaining` count in every response. Returns 429 when exhausted.
- **Data enrichment:** 5 parallel Supabase queries for additional context beyond what the client already has:
  1. Extended game log (last 10 games) from `player_game_stats` — pts, reb, ast, fg3m, min, matchup, wl, started, stl, blk
  2. Rolling averages from `player_average_game_stats` — L3/L5/L15/SZN for all stats, rest days, games in last 7 days
  3. Player's own injury status from `rapidapi_injuries`
  4. Teammate injuries (OUT/Questionable) from `rapidapi_injuries` — deduplicated by player name
  5. Opponent defense from `team_allowed_by_position` — stat allowed L5/L15
- **System prompt:** Structured prompt with all player data. Instructs the LLM to be a sports analyst that only references provided data, cites specific games/stats, and keeps responses to 2-4 paragraphs. Handles combo stats by showing each component stat individually.
- **LLM call:** Anthropic SDK → `claude-haiku-4-5-20251001`, max_tokens 1024. Conversation history (last 5 messages) passed as messages.

## Design Decisions

1. **Claude Haiku 4.5 over Sonnet** — Cost efficiency for high-volume user questions. ~$0.003/question vs ~$0.03 for Sonnet. Quality is sufficient for sports data analysis.
2. **In-memory rate limiting** — Simple and sufficient for single-instance Vercel deployment. Future: Redis for multi-instance.
3. **Server-side enrichment** — Client sends only the data it already has (prediction, L5 history, insights, lines). Server fetches additional context (extended game log, rolling averages, injuries, opponent defense) to keep the client bundle small and avoid exposing query patterns.
4. **Not persisted** — Chat resets when modal closes. Keeps implementation simple; most questions are one-off analysis.
5. **Combo stat handling** — System prompt shows each component stat individually in game log and rolling averages so the LLM can reason about what's driving the combo total.

## Second Half: Bug Fixes & Infrastructure

### 6. DFS Page Timeout Fix

**Problem:** DFS Edge Finder page returned empty error `{}`. The `get_dfs_lines` RPC query takes ~9-14s on the 67M-row `raw_player_props_combined` table, but the Supabase `authenticated` role has an 8s `statement_timeout`.

**Root Cause:** `ROW_NUMBER()` with `LPAD()` expression in PARTITION BY prevents index usage, forcing a sequential scan + external merge sort on 237K+ matching rows.

**Fix:** Applied `ALTER FUNCTION get_dfs_lines(date) SET statement_timeout = '30s'` and `ALTER FUNCTION get_game_commence_times(text[]) SET statement_timeout = '30s'`. SECURITY DEFINER functions honor function-level `SET` clauses, overriding the role-level default.

**Migration:** `add_dfs_lines_timeout_override`

**Attempted fixes that didn't work:**
- `CREATE INDEX idx_props_dfs_latest` — LPAD expression in ROW_NUMBER prevented index usage
- `DISTINCT ON` rewrite — still slow due to sort on 67M rows
- `CREATE INDEX idx_props_dfs_bookmaker_snap` — **caused 17-minute database outage** (non-concurrent CREATE INDEX on 67M rows took AccessExclusiveLock blocking all reads). Had to kill stuck processes via `pg_terminate_backend()`.

**Lesson:** NEVER run `CREATE INDEX` (non-concurrent) on `raw_player_props_combined` via Supabase migrations — they run inside transactions, so `CONCURRENTLY` is not possible. Use `ALTER FUNCTION SET statement_timeout` for slow SECURITY DEFINER RPCs instead.

### 7. MLB Sweep Fix

**File:** `src/backtesting/mlb/run_mlb_sweep.py`

**Problem:** 0 predictions across all 59 test dates (July-Sep 2025) and all 49 parameter configs.

**Root Cause:** 4 argument mismatches in `get_player_game_features()` call, silently caught by `except Exception` at DEBUG level:
1. `as_of_date=game_date` → `game_date=str(game_date)` (kwarg name mismatch)
2. `opponent_id=...` → `opp_team_id=...` (kwarg name mismatch)
3. Missing `venue_id` parameter (added to SQL query + pitcher dict)
4. Missing `season` parameter (added as `game_date.year`)

**Fix:** Corrected all 4 arguments. Added `venue_id` to the SQL query (`mlb_game_schedule`) and pitcher dict. Changed error logging from `logger.debug` to `logger.warning`.

### 8. Game Time TBD Fix

**Problem:** All predictions showed "TBD" for game time when `game_time` was NULL in `daily_predictions`.

**Root Cause:** `_enrich_game_times()` in `daily_runner.py` reads from `raw_game_lines_staging`, which was empty when the lines scraper hadn't run.

**Fix (3-layer):**
1. **`daily_runner.py`** — Added `_get_game_times_from_props()` fallback method querying `raw_player_props_combined.commence_time`

3. **`get_game_commence_times` RPC** — Rewrote to use `LATERAL LIMIT 1` joins for faster per-game_id lookups. Migration: `fix_game_commence_times_performance`

## Critical Learnings

1. **`raw_player_props_combined` has 67M+ rows** — Any DDL operation (CREATE INDEX, ALTER TABLE) is extremely risky. Non-concurrent CREATE INDEX causes AccessExclusiveLock blocking ALL queries.
2. **Supabase migrations run in transactions** — `CREATE INDEX CONCURRENTLY` is impossible via `apply_migration`. Use direct SQL or ALTER FUNCTION instead.
3. **`authenticated` role has 8s statement_timeout** — Any RPC taking >8s will silently fail with `{}`. Use `ALTER FUNCTION ... SET statement_timeout` to override for slow functions.
4. **MLB feature store kwargs differ from NBA** — `get_player_game_features()` uses `game_date`/`opp_team_id`/`venue_id`/`season`, NOT `as_of_date`/`opponent_id`.
