## Context

The model's rate features (PTS, REB, AST, THREES) predict absolute stat values without knowing the market's expectation. ACTIONITEMS.md A4 prescribes adding the player's prop line as a centering feature so the model learns **deviations from market expectation** rather than absolute values. This is the feature-based approach to residual modeling.

Prop lines already exist in `raw_player_props_combined` and are fetched by the backtest harness for edge calculation (`_prefetch_all_lines()`), but were never fed to the model as input features.

Session 3 completed A3 (Black-Litterman blending) and A2 (remove `line_total` from rate features). This session completes A4.

The LATERAL JOIN pattern:
```sql
LEFT JOIN LATERAL (
    SELECT
        MAX(CASE WHEN sub.market_key = 'player_points' THEN sub.line END) as prop_line_pts,
        MAX(CASE WHEN sub.market_key = 'player_rebounds' THEN sub.line END) as prop_line_reb,
        MAX(CASE WHEN sub.market_key = 'player_assists' THEN sub.line END) as prop_line_ast,
        MAX(CASE WHEN sub.market_key = 'player_threes' THEN sub.line END) as prop_line_threes
    FROM (
        SELECT DISTINCT ON (market_key) market_key, line
        FROM raw_player_props_combined
        WHERE player_id = pgs.player_id
          AND game_id = pgs.game_id
          AND bookmaker IN ('pinnacle', 'draftkings')
        ORDER BY market_key, snapshot_time DESC NULLS LAST
    ) sub
) prop_lines ON TRUE
```

- Used by `get_player_game_features()` (single-player inference path)
- Same deduplication logic as the LATERAL JOIN

## Design Decisions

### 1. DISTINCT ON for Deduplication

`raw_player_props_combined` has multiple rows per (player_id, game_id, market_key) — different bookmakers, different snapshots, Over/Under outcome labels. We need exactly one `line` value per stat.

`DISTINCT ON (market_key) ... ORDER BY market_key, snapshot_time DESC NULLS LAST` picks the most recent snapshot per stat from the preferred bookmakers. This is cleaner than ROW_NUMBER and works well inside a LATERAL subquery.

### 2. COALESCE to 0 for Missing Lines

Consistent with existing `line_spread` / `line_total` pattern. Real prop lines are always > 0, so XGBoost can learn that 0 means "no market line available." This avoids NaN handling complexity.

### 3. Per-Stat Feature Assignment

Each `RATE_FEATURES_*` includes only its own stat's prop line (e.g., PTS model sees `prop_line_pts` but not `prop_line_reb`). This keeps the model focused on its target stat and avoids information leakage between stat models.

### 4. No Changes to Other Modules

- `quantile_trainer.py` imports `RATE_FEATURES_*` from `feature_store.py` → automatically picks up new features
- `monte_carlo.py` `_prepare_features_batch()` handles missing features (defaults to 0) → backward compatible with existing model artifacts
- `backtest_harness.py` and `run_backtest.py` → no changes needed, features flow through existing pipeline
